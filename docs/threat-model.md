# Threat model

A short threat model for a security-minded reader. Every control below was checked against the code at the commit this document ships in, and names where it lives. If a control is not listed, it is not claimed. To report a vulnerability, see [SECURITY.md](../SECURITY.md).

## System and trust boundaries

OpenMoR is one Next.js app on Vercel with a Postgres database (Supabase). **Agents** (AI clients) reach it over MCP (`/api/mcp`) and read its public pages, markdown twins, `llms.txt` and the read-only UCP catalog; they are **untrusted and unauthenticated**. **Merchants** hand OpenMoR their Dodo API key (today through maintainer scripts) and write the product text that OpenMoR republishes, so that text is **untrusted data**. **Dodo Payments** quotes prices, hosts checkout and sends signed webhooks; it is trusted for payment truth, but its webhook endpoint is public, so every delivery is verified. **The buyer's browser** talks only to Dodo's hosted checkout and to OpenMoR's order status page; card details never reach OpenMoR. Nothing in the app calls a URL chosen by a caller.

```
agent ──MCP / HTTP──▶ OpenMoR ──Dodo SDK (merchant's key)──▶ Dodo Payments
                         ▲  ▲                                     │
        merchant text ───┘  └──── signed webhooks ◀───────────────┤
                                                                   ▼
                                              buyer's browser ─▶ Dodo hosted checkout
```

## Threats and controls

| Threat | What an attacker gains | Control and where it lives | Residual risk |
| --- | --- | --- | --- |
| **Theft of merchant Dodo keys** | Use of a merchant's Dodo account: create checkouts, read catalog and payment data | Keys and webhook secrets are stored only as AES-256-GCM ciphertext with a random IV per value and an auth tag (`encrypt` / `decrypt` in `src/lib/crypto.ts`; `createMerchant` and `setWebhookSecret` in `src/core/merchants.ts`). Decryption failures are deliberately vague (`DecryptionError`). Core returns merchants through `merchantViewSelect`, which has no key columns; `search.ts`, `public-catalog.ts` and the tools select named safe columns (a test asserts the public reads never select key columns). Provider errors have the key and webhook secret redacted (`#toProviderError` in `src/adapters/dodo/adapter.ts`). Logging: ESLint `no-console` is an error in `src/` (`eslint.config.mjs`); the only two log lines record an error class name, never bodies or messages (`src/app/api/webhooks/dodo/handler.ts`, `src/app/ucp-http.ts`). Scripts read keys with echo off (`scripts/_prompt.ts`). | Whoever holds both `ENCRYPTION_KEY` and database access can decrypt every key. There is one key and no rotation procedure. The key is decrypted in memory on each provider call. |
| **Forged or replayed webhooks** | Mark an order paid without paying; deliver a captured event again | Each merchant has its own signing secret and URL. `verifyWebhook` (`src/adapters/dodo/adapter.ts`) refuses to run without the secret and all three Standard Webhooks headers, then calls the SDK's `unwrap`, which uses `standardwebhooks` (HMAC, constant-time comparison, 5-minute timestamp window, per its source in `node_modules`). Nothing is read from the body before verification (`handleWebhook`, `src/core/webhooks.ts`). Replays are deduplicated by the `WebhookEvent` table, unique on `(merchantId, webhookId)` (`prisma/schema.prisma`). Order status only moves forward, by a conditional update (`ORDER_RANK`, `statusesBefore`, `applyPaymentEvent` in `src/core/orders.ts`). Orders are matched within the signing merchant only (`findOrderForPayment`). Body capped at 1 MiB, never logged (`handler.ts`). | A merchant controls its own signing secret, so it can mark its own orders paid (it owns them). The webhook path is deliberately not rate limited, so a flood of bad signatures costs one database read each before it is rejected with 401. |
| **Quote tampering and replay** | Pay less than quoted; reuse one quote for many orders | Agents never send amounts: `checkout` takes only a `quote_id` and a buyer email (`src/protocols/mcp/tools/checkout.ts`). Amounts, product and country come from the stored quote, which came from Dodo's checkout preview (`createQuote`, `src/core/quotes.ts`). Quotes expire after 15 minutes and are claimed atomically, once, in the same transaction that creates the order, only after Dodo created the session (`createCheckout`, `src/core/checkout.ts`). Checkout is idempotent on `sha256(quote_id + ":" + email)` (`checkoutIdempotencyKey`), backed by a unique constraint. The buyer sees and confirms the final amount on Dodo's page, and the amount actually charged is recorded from the signed webhook (`chargedTotalAmount`). | Handoff checkout does **not** re-run the price preview: a quote can drift (for example with exchange rates) before payment, and the buyer confirms the final amount on Dodo's page. The `PRICE_CHANGED` code exists but is reserved for the parked saved-method work. Quote ids are not bound to the agent that asked for them. |
| **Prompt injection through merchant-written text** | Instructions smuggled to an agent or crawler via product names and descriptions | Tool descriptions are static strings in `src/protocols/mcp/tools/*.ts`, never built from merchant data. Merchant text is capped at 200 characters (names) and 2000 (descriptions) when synced (`limitText`, `src/core/text.ts`) and returned as separate fields. On the public surfaces it is cleaned harder: invisible and bidirectional characters removed, one line, shorter limits (`publicText`, `PUBLIC_LIMITS` in `src/core/public-catalog.ts`); URLs of every scheme, HTML, link brackets and code spans neutralised (`llmsSafe`, `plainSafe` in `src/core/public-formats.ts`); quoted behind a fixed "this is data" label and never placed in a link, attribute or heading (`src/core/public-markdown.ts`, `src/app/m/views.tsx`). Tests feed hostile text through every surface. | **This reduces the risk; it cannot remove it.** Cleaned text can still be persuasive prose, and an LLM may follow it. MCP results carry names and descriptions with only the length limit, and product names also appear inside tool summaries. Agents must treat all merchant text as data. |
| **Test products passed off as real** | A buyer or agent mistakes a test-mode catalog for real goods and is misled into a non-purchase | Test-mode merchants are hidden everywhere unless `PUBLIC_INCLUDE_TEST_MERCHANTS` is exactly `true` (`src/core/visibility.ts`, used by the public reads, search, and `loadSellable` for `get_product`, `get_quote` and `checkout`). Hidden looks the same as unknown. When shown they carry a fixed `[TEST]` prefix, `is_test`, a banner on pages and twins, a line in `llms.txt`, UCP title prefix, metadata and message; pages are `noindex`, twins send `X-Robots-Tag: noindex`, and test merchants are left out of the sitemap. See [public-pages.md](public-pages.md#test-mode-merchants). | The marker is text; an agent that ignores it can still relay a test product as real. The flag is per deployment, not per merchant. |
| **Abuse of public endpoints** | Denial of service, scraping, cost or quota exhaustion | Edge: a Vercel Firewall rule (60 s fixed window, 100 requests per IP, `/api/mcp` and `/ucp/`), set in the dashboard and recorded in [deploy.md](deploy.md#rate-limiting). Request bodies: UCP 8 KB with a streamed cut-off (`readJsonBody`, `src/app/ucp-http.ts`), webhooks 1 MiB. Result caps: `search_products` 20 (`SEARCH_LIMIT`), UCP pages at most 50, catalog at most 5000 products, 500 products per merchant. Public pages, `llms.txt`, the sitemap and the UCP catalog read only cached copies of our own database and never call Dodo (`src/app/public-data.ts`). Strict `zod` validation and fixed error text that never echoes input (UCP). One 25 s deadline per tool call (`src/core/deadline.ts`). | The limit is per IP, so shared addresses share a counter and a botnet is not stopped. The rule is configured outside the code. `get_quote` and `checkout` do call Dodo (the merchant's own account) and write database rows, so the edge limit is their only throttle. The app sets no explicit cap on the MCP request body. The webhook path is excluded from the rule by design. |
| **Cross-merchant data exposure** | Reading another merchant's or buyer's data | `search_products`, `get_product` and `get_quote` return only public catalog fields of visible merchants: ids, slug, name, product text, list price, billing and fulfilment facts (`src/core/search.ts`, `src/core/products.ts`). Merchant email, keys, webhook secrets and flags are never returned. `get_quote` and `checkout` act only on the merchant and product stored in the quote. Webhook events are applied only to the signing merchant's orders. Public pages and the UCP catalog expose only opted-in, live (or flagged test) merchants and agent-sellable, active products, and never provider ids or raw provider data. | A merchant's `merchant_id` and product ids are public by design. Quotes and orders are not bound to the agent that made them (see the next row). |
| **`get_order` and a leaked order id** | Reading an order's state or its delivery | Order ids are random UUIDs (`randomUUID` in `createCheckout`). With the order id alone, `get_order` returns status, product name, quoted and charged amounts, paid time and, while unpaid, the checkout link. **Licence keys, subscription state, credits and the customer portal link need the order id plus the buyer email used at checkout**, matched exactly after normalisation (`src/protocols/mcp/tools/get-order.ts`), and are fetched live from Dodo and never stored (`getOrderFulfillment`, `src/core/fulfillment.ts`). The public order page shows only status, product and amount (`src/app/orders/[id]/status.ts`) and is `noindex`. | There are two proof factors, and the email is not a secret. Anyone who has both an order id and the buyer's email can read the delivery. Order ids appear in the buyer's return URL, so treat them as sensitive: limit access to the project's request logs (see [deploy.md](deploy.md#logging-and-secrets)). |
| **Licence key in the checkout return URL** | The buyer's licence key in browser history, logs or Referer headers | Dodo adds the key to the return URL query. The proxy strips every query string from `/orders/{id}` with a 303 and no-store, no-referrer headers before the page renders (`src/proxy.ts`, `src/lib/return-url.ts`); the site sends `Referrer-Policy: no-referrer` (`next.config.ts`); the dev server log ignores `/orders/` requests. | Vercel's own request logs can record the first request, query included, as [deploy.md](deploy.md#logging-and-secrets) says. |
| **Card data** | Card numbers, CVCs, saved cards | None passes through OpenMoR: the buyer pays on Dodo's hosted checkout every time, and the code has no card fields or card storage. Saved-method charging is not implemented ([dodo-saved-payments.md](dodo-saved-payments.md)). | OpenMoR's scope in PCI terms is small but not formally assessed. The `checkout_url` is a bearer link to a Dodo session. |
| **The database** | Reading or changing orders, merchants and secrets | Every table has row-level security enabled with no policies, and the Supabase API roles `anon` and `authenticated` have their privileges and default privileges revoked (`prisma/migrations/*enable_rls_revoke_api_roles`, `*revoke_default_privileges_api_roles`, and the same step for `WebhookEvent` in `*checkout_webhooks`). The app has no Supabase client library and no browser-side database access; it connects server-side through Prisma (`src/lib/db.ts`). Queries are parameterised by Prisma. `WebhookEvent` stores no payload. | The app's own connection is the table owner and bypasses RLS, so RLS guards against the Data API, not against a bug in OpenMoR. A leaked `DATABASE_URL` is full access. |
| **SSRF** | Making OpenMoR call internal or arbitrary addresses | The app fetches no caller-supplied URL. The only outbound calls are the Dodo SDK to Dodo's fixed hosts, selected by the merchant's mode (`src/adapters/dodo/client.ts`); the checkout return URL is built from `APP_URL` (`createCheckout`); stored product image URLs are never fetched. The UCP `UCP-Agent` profile URL is ignored by design, so no caller-chosen address is ever requested ([ucp-acp.md](ucp-acp.md#deliberate-deviation-the-callers-ucp-agent-profile-is-not-fetched)). | This departs from the UCP rule that a business must fetch the caller's profile. It is a deliberate choice. |

## Known limits and non-goals

- **No per-merchant or per-agent authentication on MCP yet.** Any caller can use any tool against any visible merchant. Agent sessions are attribution only (`src/core/agent-sessions.ts`), not a security boundary.
- **No merchant dashboard or sign-in yet.** Merchants are onboarded by maintainer scripts, so there is no merchant-facing account to attack, and no merchant self-service either.
- **IP-based rate limiting only**, at the edge, outside the code, and not applied to webhooks.
- **In-memory catalog search.** The UCP catalog is searched in memory over a cached read capped at 5000 products. It is not built for a large catalog.
- **Saved payments.** The buyer pays on Dodo's hosted page every time, and agent-initiated repeat purchases are blocked until Dodo exposes a reusable saved method: [dodo-saved-payments.md](dodo-saved-payments.md).
- **No price re-check at handoff**, no key rotation procedure, and provider error text (with our key redacted) is relayed to agents as `PROVIDER_ERROR`.
- **Non-goals:** defending against a compromised merchant account, Dodo, Vercel or Supabase; and preventing an LLM from following instructions in text it reads.
